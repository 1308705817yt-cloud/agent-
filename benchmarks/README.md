# 独立故障案例与评测

数据集版本：`independent-v2`，共 **10 个案例，5 个故障、5 个正常样本**。任务与 v1 相同，v2 为每条检查增加冻结的预期用例 ID 与实际执行完成证据。全部独立于客户查询 demo，使用实际 Python 函数执行并通过公开的 `TraceRecorder` 生成观测。

## 案例

| 家族 | 故障样本 | 正常样本 |
| --- | --- | --- |
| 参数 | 工具关键字改名未同步；整数被转换成字符串 | 正确参数映射 |
| 状态合并 | 用部分更新替换完整状态，丢失请求约束 | 合并后保留原状态 |
| 循环终止 | 工具已完成，仍继续重复调用 | 完成后停止；按预算有意轮询 |
| 提示词 | 同时要求 JSON 对象和禁止 JSON | 一致的 JSON 输出要求 |

案例源码位于 [benchmark_data/cases](../agentdoctor/benchmark_data/cases)，标签与独立验收样本位于外层 [suite.json](../agentdoctor/benchmark_data/suite.json)。每个项目含自己的源码、工具契约、可见开发检查、记录配置。没有参考补丁。

提示词案例使用**确定性响应模拟器**，用于测试冲突提示词能否被检测、修改及验证，不代表真实目标 LLM 的行为质量。正常轮询是故意保留的困难负样本：重复调用并不一定是故障。

## 执行

在仓库根目录：

```powershell
.\.venv\Scripts\python.exe -m agentdoctor benchmark
```

无模型模式无需网络。使用模型可执行：

```powershell
.\.venv\Scripts\python.exe -m agentdoctor benchmark --provider ollama --model <模型名> --executor docker
```

支持已有 OpenAI 适配器与对应环境变量。模型模式默认 Docker，需预先准备 `python:3.11-slim` 镜像；`--executor local` 为显式的可信本地执行选择。每个样本创建新的模型客户端并应用相同调用/补丁预算。`--repetitions N` 重复整套实验，不等于修复器内部的验收重复次数。

### 固定案例集，使用 Codex CLI

[independent-v2.lock.json](independent-v2.lock.json) 固定当前 10 个案例、43 个文件，与规则模式基线的数据集哈希一致。运行先生成独立快照并核对清单；任何文件内容或增删变化都会在模型调用前拒绝运行。每次运行在自己的 `dataset/` 中保留完整冻结副本。

在 Windows 上先登录 CLI，再运行：

```powershell
codex.cmd login
codex.cmd login status
.\.venv\Scripts\python.exe -m agentdoctor benchmark --provider codex --executor local --dataset-lock benchmarks/independent-v2.lock.json --output artifacts/model-benchmarks
```

该命令对自带案例显式采用本地执行器。需要容器时改为 `--executor docker` 并准备对应镜像。CLI 身份认证通过预检才会调度案例；未登录不会产生一份全零“模型评测结果”。已使用 `codex-cli 0.146.1` 完成下文记录的真实服务评测。运行进程需要能访问 CLI 的登录缓存；本次沙箱内检查显示未登录，普通用户环境可识别已登录状态，实际调用在普通用户环境进行。

如果评测 CLI 与日常 Codex 使用不同账号，可在单独的 PowerShell 窗口指定独立目录后登录；该环境变量仅影响当前窗口及其子进程。先创建目录，再执行登录与上面的评测命令：

```powershell
$env:CODEX_HOME = "$env:USERPROFILE\.codex-agentdoctor"
New-Item -ItemType Directory -Force -Path $env:CODEX_HOME | Out-Null
codex.cmd login
codex.cmd login status
```

本次实际评测沿用默认配置目录中可用的 CLI 登录，未切换账号，也未使用不存在的独立目录。

Codex 通过[官方非交互执行接口](https://learn.chatgpt.com/docs/non-interactive-mode)接收结构化上下文；每次调用使用新的临时工作目录、只读模式、结构化输出 Schema 和临时会话，禁用工具、插件、记忆、用户配置与 AGENTS 文档加载。模型输出必须同时具有完成事件、成功退出和符合 Schema 的结果；出现工具动作则排除该响应。身份认证沿用 CLI，不要求向本项目提供 API 密钥。工具禁用与上下文隔离用于避免外层标签、其他案例和独立验收样本进入提案过程。

可通过 `--model <模型名>` 显式选择模型；未指定时记录为 `codex-default`，表示使用该 CLI 的默认选择，不能据此声称锁定了具体模型版本。报告记录 CLI 版本、实现哈希、调用次数和 token 用量。每个案例的 `model-events.json` 保存操作类型、时间、结构化响应或错误；不保存原始推理流。模型 API 错误与成功返回空补丁分开统计。

本轮仍使用既有的“显式别名规则优先，其后模型提案”策略。候选 `origin` 区分 `declared_alias` 与 `model`，规则修复不归为模型生成的修复。正常样本只进行诊断，故障样本进入修复流程。规则基线文件不被模型运行覆盖。

产物位于 `artifacts/benchmarks/benchmark-<id>/`：

- `benchmark.json`：指标、分子/分母、逐案例发现、原版本与候选独立检查结果。
- `cases.csv`：便于查看和比较的案例级结果。
- `candidates.csv`：每次候选的来源、结果分类和失败原因。
- `dataset-manifest.json` 与 `dataset/`：本次实际使用的文件清单和冻结案例。
- 每个案例自己的 engine report、补丁、源快照和独立验收副本。
- `artifacts/benchmarks/last-benchmark.json`：最新一次报告路径。

退出码 0 表示所有案例完成测量，不表示全部诊断或修复正确；环境或采集问题导致测量不完整时为 2。报告包含数据集版本、数据集哈希、实现源码哈希、模型、执行器和重复次数。语义诊断 API 失败会列为不完整测量，不能充当正常样本预测。

从 0.3.1 起，评测报告 `schema_version=2`，分别记录 `diagnosis_status`、`repair_status` 和候选的 `assessment_status`。原版本已满足基线契约后，候选耗尽独立检查时间预算计为失败；目标超时阻止修复成功，回归超时还计入回归失败。即使主流程交付 `verified`，这些失败也会进入错误验证率。候选破坏文件完整性同样计为失败。

进程无法启动、Docker 调用错误、执行目录不可用等明确环境故障单独记为 `environment_error`，不伪装成通过或候选代码错误。已完成的诊断仍进入诊断指标，所有已尝试的候选仍进入 `candidate_count`。目标与回归分别保存 `heldout_outcomes`；一项超时不抹去另一项已完成的结果。该分类按观测到的执行结果判定，不声称能识别所有主机负载或调度问题的根因。

## 独立性

1. 只把单个案例的源码、工具契约、采集配置和可见开发检查复制进修复项目。
2. 轨迹采集只读取各案例的采集配置与源码，不读取标签和额外验收样本。
3. 修复器使用真实检测与修复流程，没有根据案例 ID 返回固定答案的逻辑。
4. 独立验收使用外层固定的预期结果和另外一个执行器脚本，不导入项目中的 `evaluator.py`。它只在模型结束提案后，放入另外的执行副本。
5. 验收使用未出现在开发检查中的输入。只硬编码开发样本的补丁会被判为独立验收失败；相应行为有回归测试。
6. JSON 标签只在评分器中用于比较，不传入诊断/修复模型上下文。案例也不会互相进入上下文。

`evaluator.py` 故意包含在允许修改的路径中，但验证命令通过 `python -m evaluator` 调用，程序应自动冻结它。这同时覆盖新修复的验收保护路径。

开发检查与独立检查均需提供 [完成证据](../docs/validation-evidence.md)：本次执行标识、实际数量和逐项结果必须匹配固定的预期用例集合。导入/调用时的 `SystemExit` 会被捕获为失败；`os._exit(0)` 等直接退出导致的空输出也不能通过。独立检查缺失结果属于候选验收失败，不会仅因进程退出 0 而成功，也不会从候选计分中静默排除。

## 指标口径

所有比率同时保存 `numerator`、`denominator` 和 `value`。分母为 0 时 `value=null`，不会把未尝试修复写成 0% 回归失败。

`repair_breakdown.case_outcomes` 对 **5 个故障案例 × 重复次数** 作互斥分类；正常样本不计为“没有生成补丁”：

| 分类 | 判定 |
| --- | --- |
| `no_patch_generated` | 正常结束提案流程且没有任何候选；模型成功返回 `edits=[]` 或规则没有可用提案 |
| `policy_rejected` | 已有候选，但路径保护、补丁匹配、引用、语法或预算等应用前检查拒绝，未到可见验收 |
| `visible_test_failed` | 候选已应用，可见目标或回归检查失败、缺失完成证据、超时或违反文件完整性 |
| `independent_acceptance_failed` | 候选通过可见检查，但独立目标或回归检查明确失败，包含候选超时 |
| `repaired` | 主流程交付 `verified` 且独立目标与回归均通过 |
| `model_error` / `environment_error` / `not_evaluated` | 分别表示模型调用未完成、执行环境无法判定、尚未进入有效修复；不并入上述四类失败 |

重试后成功的案例只计一次 `repaired`；未成功且没有调用/环境阻断的案例，按所有候选到达的最远验收阶段分类。后续模型或环境阻断会单列，之前已发生的候选失败仍保留在 `candidate_outcomes` 中。`candidate_outcomes` 对每次候选按首个失败关卡分类，因此通过一次重试修好时，前面的失败候选依旧可审计。`candidate_attempts` 与 `candidate_origins` 给出总次数及来源；四类失败、成功和未完成项应一起展示，不能仅展示四类失败来缩小分母。

| 指标 | 口径 |
| --- | --- |
| 诊断准确率 | 实质故障类别集合与标签完全一致，且故障定位到正确源文件的案例数 / 已完成诊断的案例数。正常样本需要没有实质故障告警 |
| 二分类检测准确率 | 判断“存在/不存在实质故障”正确的案例数 / 已完成诊断的案例数；另给 TP/TN/FP/FN、精确率、召回率 |
| 修复成功率 | 被修复器判为 verified，且额外目标/回归检查均通过的故障案例数 / 已能判定修复结果的故障案例数。包含未生成补丁的故障、候选超时和验收失败 |
| 候选回归失败率 | 对原先通过的回归功能产生明确失败的候选数 / 已能判定回归结果的候选数。可见或独立回归任一处失败（含超时）即判失败；否则需独立回归通过 |
| 错误验证率 | 已交付为 verified 且独立验收明确失败的故障案例数 / 已能判定独立验收结果的 verified 交付数。超时属于失败；缺乏环境条件导致无法判定的交付另行计数 |

`measured_cases` 仍表示所有阶段完整的案例数；`diagnosed_cases` 和 `repair_measured_cases` 分别表示诊断与故障修复指标的测量数量。`candidate_count` 与 `delivered_count` 保留全部已尝试候选与已交付数量，包括后续遇到环境故障的记录。`incomplete_candidates`、`unassessed_deliveries` 明示尚不能完整评估的候选和无法判定的交付；不得只报告过滤后的比率而省略这些数量。已经确定一项独立检查失败时，足以判定该交付错误，即使另一项检查环境不可用。

`execution_error`、`task_failed`、`task_assertion`、`validation_failure`、输入/输出 Schema 错误、无效 JSON 和无证据完成声明属于**症状级标签**，不直接算正确根因类别。主类别为 `tool_argument_schema`、`state_invariant`、`possible_loop`、`prompt_conflict`。其他未知的实质类别不会被丢弃，会作为额外预测影响准确率。

这里的“诊断准确率”测的是**类别与源文件定位**，不评判自然语言根因解释的完整性，也不是因果证明。标签由案例的预期行为预先定义，不由修复模型评分生成。未满足基线契约的案例不能进入后续测量；后续阶段的环境故障不删除已完成阶段的结果。比较两次结果时必须同时检查各指标分母和未评估数量。

## 当前规则模式基线

机器可读汇总保存在 [baseline.json](baseline.json)，为 0.3.1 / independent-v2 下重新运行的结果。0.3.0 旧结果保留在 [baseline-v0.3.json](baseline-v0.3.json)，它尚未采用分阶段统计。0.2.0 旧结果保留在 [baseline-v0.2.json](baseline-v0.2.json)，其验收没有执行完成证据，不能作为已排除提前退出误验收的证明。当前结果：

| 指标 | 结果 |
| --- | --- |
| 完成测量 | 10 / 10 |
| 诊断准确率 | 8 / 10 = **80%** |
| 修复成功率 | 1 / 5 = **20%** |
| 候选回归失败率 | 0 / 1 = **0%** |
| 错误验证率 | 0 / 1 = **0%** |

规则基线的错误来自正常轮询的误报和提示词冲突的漏报。唯一自动修复的是已有显式别名契约的参数错误。状态、终止和提示词的一般修复需要模型或新增修复策略；该规则基线没有调用真实模型。

**只有一个候选的 0% 回归失败率不代表通用修复可靠性。** 这组数据用于暴露能力缺口和回归比较，不能据此推断生产场景的准确率或统计置信度。

## 0.4.0：入口、根因上下文与诊断回归

## 0.5.1：结构化归因与调用链轮询

先补齐归因接口，再扩展轮询规则。本版保留原有类别、案例、标签和历史结果，不重算 0.5.0 的分数。

`source`／`observed_source` 表示错误观察位置；`root_causes` 保存独立的根因位置和证据。在线 Schema 要求新告警明确指定 `observed_at`，通过 `attributions` 将上游原因关联到已有告警，避免只能用新类别表达原因。根因引用必须包含原观察、实际提供的当前轨迹和连续源码摘录；校验通过后仍是待验证假设。JSON、HTML 和后续补丁上下文保留两种位置及其区别。
